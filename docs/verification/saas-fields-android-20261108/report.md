从编辑器键盘菜单分别打开“都来帮”和“领航员”，实际进入 SaaS 既有全屏“选择成员”页面，每次选取同样两名不同成员后完成。

| 主正文 | FM-H1 | FM-P1 | 两类均成功 |

## 2. 保存、重开和数组核对

- 第一次更新保存与详情回读成功；退出预览后查看原列表，再从首页工作成果槽位重新打开编辑器。
- `helpItems` / `help_items` 和 `navigatorItems` / `navigator_items` 各 **4 条**，每条 **2 名不同成员**。一个多人条目对应一个数组元素，没有按人数重复生成元素。
- 数组顺序与正文中各来源的顺序一致，逐行文字、人员 ID、姓名均与原正文一致；脱敏归档只保留 U01/U02 别名。
- 四个来源中各业务标记恰好一次。主正文、感悟、自检完整抽离到对应原字段，自定义内容仍完整保存在 `bodyContent`。
- 保存请求正文与详情 `body_content` 完全相等；重开正文与第一次保存读回完全相等。
- 与验收前基线逐段比较，原主正文和感悟普通文字及既有人员完整保留，仅忽略空行差异。

## 3. 真正删除和清空后再次保存

使用退格删除每条人员业务行中的文字、两名成员及空行本身，删除全部 8 条帮助/领航条目；将自检普通文字一并清空。没有用栏目“关闭”代替删除。

- 第二次更新请求明确发送 `helpItems: []`、`navigatorItems: []`，空自检按现有契约省略 `selfCheck`。
- 后端详情实际返回 `self_check: {content: '', mentions: []}`，两个业务数组均为空。这里按文字与人员均为空判断清空，不强制空对象必须是 `{}`。
- 清空后的保存读回和退出后再次重开，共 **2 次详情读取**，正文均与第二次提交一致；整个正文已无本轮 8 个业务标记，自检来源为空。
- 第二次保存后刷新首页及原列表，对 `/dailyOrient/readDailyOrient`、`/dailyOrient/readOrgWorkOrient` 中该记录的两个结果分别核对：自检无旧文字/人员，帮助和领航数组为空，主正文和感悟无本轮业务条目残留。
- 原列表界面不再显示该记录的自检、都来帮、领航员区块。重开编辑页无旧业务行，空自检不再展示；自定义栏目普通文字 CUSTOM-BASE 保留。
- 原主正文、感悟和既有人员仍与验收前基线一致。
